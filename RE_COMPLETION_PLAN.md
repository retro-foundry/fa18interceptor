# Reverse-engineering completion plan

Updated: 2026-09-25. Authority: preserved 1988 disk, sealed captures, canonical
runtime snapshots, and the pinned Engine9000 v0.62-alpha Amiga core. The target
is readable, byte-exact 68000 game source and a behaviorally explained game,
including the renderer's world representation and its detail-selection rule.
The Amiga OS and mutable display buffers are separate from game source.

## Completion gates

1. **Authority and coverage:** Every loaded game region has a reviewed
   executable, data, mutable workspace, or unresolved classification with its
   evidence. Every game instruction reached by the scenario set has byte-exact
   source and an explicit call/return or branch boundary. The `unresolved`
   category reaches zero before claiming complete source coverage; unseen
   segments require positive data evidence or a scenario that executes them.
   All assembled ranges pass `scripts/verify_reconstructions.py` with no
   overlaps. OS code and original assets remain separately identified.
2. **Behavior:** Each major system has a producer/state/consumer explanation,
   original addresses, and at least one repeatable oracle: menu and mission
   state, input, flight dynamics, camera, collision, weapons/targets, AI or
   scripted actors, audio, persistence, and renderer/display. Strong names
   require behavioral or scenario evidence; structural labels remain marked.
   A game loop reconstructed only as many anonymous helper calls does not pass.
3. **World:** Export the original static selector directories, page/template
   streams, placement rules, local 3D components, control records, and observed
   primitive topology with provenance and format boundaries. Establish the
   transform from selected source to displayed map/flight geometry and the
   coordinate convention through controlled replay. A stitched screen image
   or X/0/Z placement cache alone does not pass as a complete 3D world.
4. **Terrain detail (out of scope):** The user explicitly removed LOD analysis
   from this reverse-engineering objective on 2026-09-25. Their working
   reconstruction guidance is that terrain uses two tile sizes; preserve this
   as user-scoped terminology, not a newly proved binary-semantic claim.
   Preserve existing selector and projection evidence without treating a
   physical-range or Golden Gate detail-rule conclusion as a completion gate.
   Do not create or prioritize new LOD captures unless the user later restores
   this scope.
5. **Validation and handoff:** Preserve exact replay inputs, start states,
   snapshot/tool hashes, bounded traces, source/asset manifests, and compact
   fixtures. Rebuild reports from scripts, cross-check independent replays,
   and update `README.md`, `STATUS.md`, and `TRANSFER_NEW_CHAT.md` with the
   final measured state and remaining qualifications.

## Work sequence

### 0. Make the scorecard reliable

- Regenerate `analysis/coverage.json`, `analysis/capture_targets.md`,
  `analysis/runtime_region_inventory.md`, and
  `analysis/ghidra_function_coverage.md` from their scripts. Keep
  `analysis/semantics.json` synchronized with the strict generated coverage
  fields, while reviewing semantic levels separately from assembly length.
- Record each routine's entry, full observed return, callers, state reads and
  writes, meaning level (`structural`, `dataflow`, `behavioral`, `scenario`, or
  `port-contract`), and the fixture or trace that supports it. Track game code
  separately from OS/library wrappers and static-only source.
- Work backward from known screen, audio, or state effects using verified
  emulator call/return stacks. Rank unknown caller boundaries by the distinct
  observed effects and scenarios they connect, then prove their inputs and
  branch outcomes before promoting names. The initial world/renderer ranking
  is in `analysis/reverse_call_stack_priorities.md`.
- Gate: one command or documented command set reproduces the same baseline;
  no two headline files disagree about what a percentage counts.

### 1. Expand replay coverage by gameplay state

- Audit existing sealed runs against a scenario matrix: menu setup, demo,
  training/qualification, free flight, takeoff, each of six missions, combat
  and weapon use, landing, crash/ejection/rescue, map/camera changes, return
  screens, and pilot-log persistence. Mark each `sealed`, `partial`, or
  `missing`, with the exact start state and entry/exit frame. Do not infer
  coverage from a run's name.
- Record missing states using `scripts/record_run.py` and seal them with
  `scripts/finalize_run.py`; use Engine9000 replay plus short focused traces
  to identify executed PC ranges, state transitions, and display/audio effects.
  Prefer scenarios that enter large dark game-code regions or distinguish a
  high-impact unknown. Current `analysis/capture_targets.md` ranks low-use
  and dark segments; its single reconstructed-reachable P-code gap at
  `$C06BF0` already has a separate bounded native-Delete trace.
- Gate: each scenario has a deterministic full-frame replay and at least one
  meaningful state/input/output checkpoint. Refresh the code/data inventory
  after each new execution family.

- Gate: source records and transforms reproduce independent map/flight
  scenarios; every exported world feature has a trace-backed source boundary
  and a known coordinate convention. Gaps in world coverage are enumerated

### 3. Golden Gate detail rule (deferred by user scope)

Existing evidence is retained as a qualified renderer observation only. It is
not a required completion gate and should receive no new capture work while
this scope decision remains in force.

### 4. Reconstruct the remaining game systems

- Follow input rows through raw-key/joystick state, update order, fixed-point
  flight state, camera and HUD, collision, weapon/target state, mission scripts,
  audio writes, and save/load records. Start with the replay scenarios from
  phase 1 and the proved math, projection, blitter, and text primitives.
- For each cluster, capture a bounded entry/exit oracle with registers,
  relevant RAM windows, and screen/audio changes where applicable. Convert
  only evidenced paths to readable 68000 source; label static-only paths
  honestly. Add narrow fixtures for boundary cases before promoting broad
  names or gameplay claims.
- Gate: a reader can follow each major user action to state change and visible
  or audible result, and the source is byte-exact across all classified game
  code. Re-run the scenario matrix after major call-graph discoveries.

### 5. Final audit

- Run the assembler byte gate, region inventory, replay determinism checks,
  scenario oracles, and world/pixel comparisons. Audit all `candidate`,
  `unknown`, and `unresolved` claims. Resolve them or state precisely why
  completion cannot yet be claimed.
- Deliver an address-linked source index, semantic system guide, scenario
  fixture index, world asset manifest/viewer, and detail-selection report.
  The completion report must state byte, execution, semantic, and scenario
  coverage separately.
