# Human coverage run024

`captures/run024/` is a sealed replay from the preserved post-load menu state.
The player reports several failed carrier-qualification attempts followed by a
free-flight pass beneath the Golden Gate Bridge. Those scenario labels are user
context, not yet code-level classifications.

## Frame-23,000 renderer sample

`build/run024_frame23000_checkpoint/` is a sealed state produced by ordinary
replay through the user-identified San Francisco / distant Golden Gate view.
One following no-input frame, recorded in
`build/run024_frame23000_oneframe_custom/`, has 616 Custom-register writes and
ends with video digest
`a165f3c8d213d5036745de2828bac99dc737471465fb7dc09381d3626770d916`.
Its non-Copper blitter register writes include sources in the known
`$C2FBxx-$C2FDxx` active-plane line-submission family. This links the visible
landmark frame to active line-renderer activity, but does not yet assign an
individual submitted line, control stream, or edge list to the bridge.

A return-validating no-input breakpoint at `$C2FA7E` in the same checkpoint
does reach the line setup, but its first captured endpoints are `(157,72)` to
`(161,72)` and it returns to `$C341B2`. The adjacent caller at `$C341AC`
constructs this line from fixed screen coordinates plus `$C458D8/$C45988`.
It is therefore an overlay candidate, not bridge-model evidence. The Custom
log proves renderer activity in the landmark frame; it does not by itself
prove that the landmark's pixels use this particular line path.

qualification flag or result-state byte is inferred from this display-phase
sample.

## Qualification-screen execution sample

`build/run024_qualification_gate_trace/` replays normally through frame 600,
then instruction-steps chipset frames 601--602 with no future input. It is the
first bounded trace anchored to the visible qualification-gate screen:

- 21,423 instructions; 458 observed Slow-RAM starts; 2,249 exported P-code
  operations; 36 structural call-target candidates.
- The snapshot and trace are byte-validated before Ghidra import. Its visible
  frame-600 video digest is
  `9bcbc0e70de8da2758af1801721564a271f23e6aab4067554b5fe398bed0912`.
- `$C0FECE` is a newly inventoried structural Ghidra entry in this export, but
  it is not among the executed starts in the two-frame interval. No source
  reconstruction, qualification-byte identification, or gameplay name follows
  from this discovery.

The trace is a display-state execution sample, not yet a producer/consumer
trace for persistent qualification status. A future focused capture must put a
breakpoint on a candidate gate reader or trace a transition into/out of this
screen.

The transition into this screen is now bounded at the menu-selection layer:
the sealed replay's frame-584 frontend key `5` reaches `$C1BD78`, normalizes
to `$C458A6=9`, and `$C0FCB4` appends text selector 105, resolving to the
qualification gate line.  See
`analysis/run024_qualification_selection_chain.md`.  This proves menu-path
selection only; it still does not identify qualification persistence.

The delayed follow-up has also been traced through its mode-9 route at frame
627, ending at callback `$C101FC`; see
`analysis/routines/c0fece_delayed_menu_transition.md`.  The gameplay ownership
of that state transition remains unassigned.

The ASCII token `QUALIFICATION` occurs in the trace snapshot's Slow RAM at
`$C3F309`, `$C3F42E`, and `$C3FAFF`. The same text resource is already present
in the preserved baseline snapshot. These are preloaded message bytes, not
candidate qualification-status storage; subsequent work must trace the code
that selects a message rather than treating any of these locations as a flag.
